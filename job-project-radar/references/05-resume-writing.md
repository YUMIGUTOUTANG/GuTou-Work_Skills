# 05 · 简历写作指南（项目经历）

## 总原则

- 用 STAR 结构组织：背景（Situation）→ 任务（Task）→ 行动（Action）→ 结果（Result）；
- 核心问句链：**什么场景为什么做 → 用什么方法怎么做 → 遇到什么问题怎么解决 → 产生什么量化结果**；
- 把"我做了什么"升级为"我解决了什么问题、带来什么价值、体现什么能力"；
- 每个要点写清"问题 → 方法 → 效果"的因果链，禁止只罗列技术名词和流程名。

## 三个版本的结构（按简历空间自选）

### 精简版（约 5~7 行）

- **行头**：项目名（含场景标签）｜【时间】｜角色；
- **3~4 条 bullet**：每条"问题→方法→结果"，至少 2 条带量化数字；
- **技术栈**：一行。

### 中间版（约 12~18 行）

- 行头同上；
- **项目背景**：1~2 句（什么场景、服务谁、解决什么问题）；
- **核心模块 bullet ×3~4**："模块名（技术手段）：针对 X 问题，采用 Y 方法，使 Z 从 A→B"；
- **成果 bullet ×2~3**：技术指标 + 性能 / 规模 / 业务指标；
- **技术栈**：按类别分行。

### 详细版（约一页）

- 行头同上；
- **项目背景**：1~2 句；
- **主要挑战**：3~5 条具体问题（如数据非结构化、语义鸿沟、多轮连贯、成本与性能平衡）；
- **核心技术 / 系统模块设计**：按链路分模块（数据与知识构建 → Query 理解 → 检索召回 → 生成与后处理……按项目实际调整），每条写清方法与目的与效果；
- **项目成果**：3~4 条量化（含 1~2 个性能 / 规模指标）；
- **技术栈**：按类别分行；
- **个人贡献**（团队项目时）：写清主导 / 实现的具体模块。

## 行头规范

- **项目名称**：带场景标签，如「XX 问答系统开发与优化（工业设备知识库）」——避免纯技术名词堆砌；
- **时间**：写为【时间】，并附提示"请替换为你自己的真实起止月份（与个人时间线吻合）"；
- **角色**：给建议值，如"独立开发 / 算法工程师（个人项目）"，用户可改。

## 各段落写法

### 项目背景

1~2 句：什么业务场景、服务哪类用户、解决什么问题。禁止行业宏大叙事开头。

### 主要挑战

3~5 条**具体**问题，每条都要在后文找到对应解法。常见挑战类型：数据多源异构、语义鸿沟、多轮连贯、幻觉控制、成本与性能平衡、并发与稳定性。

### 模块设计

- 按系统链路组织："模块名（技术手段）：针对 X 问题，采用 Y 方法，使 Z 从 A→B"；
- 深度优先级：**能"魔改现成工具"或"自研组件"的点优先写**（有取舍、有理由、有效果），"直接使用成熟组件"一笔带过；
- 关键方法给到实现细节：模型与策略名称、参数配置（如检索 topK、分块策略、LoRA rank/alpha/lr、并发配置）——细节体现真实动手；
- 用了开源组件，写清"为什么选它、它有什么局限、你怎么绕过或改造"。

### 项目成果

- 2~4 条量化，优先"指标从 A 提升至 B"句式；
- 指标选型原则：场景认可的核心指标（检索质量 / 回答质量 / 性能 / 规模 / 成本 / 业务转化）；
- 补 1~2 个性能或规模指标（延迟、吞吐、调用量、数据规模）；
- 业务型项目补业务指标（满意度、转化、时间节省）；
- 不用无意义的小提升撑场面（如 +2% 的边缘指标）。

### 技术栈

分类分行，示例类别：模型与训练 / 检索与向量库 / 框架与编排 / 数据与文档解析 / 部署与观测 / 评估。

## 措辞规范

- **强动词开头**：主导、设计、构建、实现、优化、搭建、集成、迭代、重构；
- **弱动词禁用为成果**："参与、协助、熟悉了、掌握了、了解了"——那是学习总结，不是项目产出；
- **句式模板**："针对 X 问题，采用 Y 方法，使 Z 指标从 A 提升至 B"；"为解决……引入……"；
- **技术名词写准写全**（如 BGE-M3、BM25、Cross-Encoder、HyDE、QLoRA、DPO、MCP），首次出现可括号点明用途；
- **删除宣传腔与套话**（"强大的""赋能""全面提升"），只留事实、方法与数字；
- 控制层级：标题 → 模块编号 → bullet，让人 10 秒看到重点，禁止大段无结构文字。

## 定位与诚实边界（保护用户的面试安全）

- 默认建议定位为「**基于开源项目的深度使用与二次开发**」：面试官可能搜到仓库，定位一致才经得起追问；
- 如果用户确实做了大量改造或重写，可升级为"参考实现并自主重构"一类表述；
- 每个写下的数字与细节都必须经得起追问：基线、口径、计算方式要能说清（数字纪律见 06）；
- 不要写用户完全不理解的内容——面试现场讲不出来的细节，就是埋给自己的雷。

## 七类失败模式（写作时逐一规避）

| 失败模式 | 表现 | 规避规则 |
| --- | --- | --- |
| 课程作业式 | 技术堆砌 + "熟悉了 / 掌握了" | 写业务场景、问题与结果，而非学习心得 |
| 职责罗列型 | 全是"主导调研 / 协调 / 维护" | 每条都必须落到技术实现与效果 |
| 术语堆砌型 | 名词串烧无因果 | 每个名词都放进"问题→方法→效果"链条 |
| 有结果无过程 | 写了数字但说不清怎么来的 | 数字前有方法，数字后配口径与来源 |
| 流水账缺三要素 | 只说"完成了全流程" | 补齐动机、做法、评估三个要素 |
| 表面完成度高但失真 | 评估体系不可信、业务不着边际 | 数字量级与项目体量自洽，业务场景能自圆其说 |
| 逻辑混乱型 | 前后数字矛盾、结构跳跃 | 交付前统一核对：三版本数字一致、概括句与细节一致 |

## 完整骨架示例（详细版，领域 RAG 示意）

> **示例只演示结构与措辞，数字均为示例量级，使用时按真实情况校准。**

**智能客服知识问答系统开发与优化（电商售后场景）** ｜【时间】｜独立开发

**项目背景**：售后知识分散在多个渠道且更新频繁，人工客服响应慢、口径不一。面向售后客服与终端用户，构建了 RAG 知识问答系统。

**主要挑战**：① FAQ、工单、产品手册多源异构，解析质量参差；② 售后术语口语化，检索语义鸿沟明显；③ 多轮对话中上下文漂移；④ 高峰期成本与响应延迟压力。

**系统模块设计**：

- 数据与知识构建（多源解析 + 结构化清洗）：针对不同来源格式差异定制解析与分块策略，知识入库完整率 98%；
- Query 理解（口语化改写 + 多路召回）：针对术语鸿沟引入查询改写与 BM25 + 向量混合召回，Top5 召回率从 65% 提升至 90%；
- 生成与后处理（引用溯源 + 低置信兜底）：针对幻觉问题引入引用约束与兜底策略，回答准确率从 54% 提升至 89%（测试集 800 条，LLM+人工双评）；
- 性能优化（缓存 + 并发控制）：高峰期平均响应从 3.2s 降至 1.4s。

**项目成果**：Top5 召回率 65%→90%；回答准确率 54%→89%；平均响应 3.2s→1.4s；人工客服转接率下降 30%。

**技术栈**：Python / LangChain / BGE-M3 / BM25 / Milvus / FastAPI / Docker

## 一致性核对（交付前必做）

- 三个版本之间：同一指标的数字完全一致；
- 版本内部：概括句与细节句数字一致；
- 不使用无单位、无基线、无口径的数字（正例"Recall@10 从 30% 提升至 95%"，反例"月均调用 8w+"）；
- 每个数字都有评估来源表述（测试集规模 / 人工标注 / LLM+人工双评）。
