# 02 · 检索与评分

## 一、检索来源与工具策略

**零配置可跑，有则增强。**

1. **有 `gh` CLI 且已登录**（`gh auth status` 通过）：优先使用——
   - 仓库搜索：`gh search repos "关键词" --stars 200..20000 --updated ">2025-04-01" --limit 50`（具体参数以 `gh search repos --help` 为准）；
   - 代码搜索：`gh search code "技术关键词"`；
   - 仓库详情与活跃度：`gh api repos/<owner>/<repo>`。
2. **无 gh / 无令牌（零配置路径）**：用 HTTP 请求 GitHub REST 仓库搜索（匿名限速约 60 次/小时，注意节约调用）——
   - `https://api.github.com/search/repositories?q=<关键词>+language:python+stars:200..20000+pushed:>2025-04-01&sort=stars&order=desc&per_page=30`
   - 需要更多信息时，抓取仓库页面 / README（raw.githubusercontent.com）兜底。
3. **辅助来源**：awesome 清单（`topic:awesome`、领域 awesome 列表）、GitHub Trending 页面、技术社区讨论——作为线索发现渠道，最终仍以 GitHub 仓库为准。

**中国网络提示**：clone 或访问缓慢时，建议用户配置代理或使用镜像加速（如 ghproxy 类前缀），把可用方案给用户，不强制。

## 二、检索关键词构建

按「岗位族 → 项目类型模板 → 关键词组合」三层构建。

### 项目类型模板（按岗位族）

| 岗位族 | 可检索的项目类型 |
| --- | --- |
| AI 应用 / Agent | RAG 系统与知识库问答、Agent 框架与工作流引擎、工具生态（MCP / 函数调用）、记忆与上下文管理、评估与可观测工具 |
| AI 全栈 | 端到端 AI 产品（对话界面 + 服务端 + 模型接入）、LLM 应用平台 / 脚手架、AI 工作流产品 |
| 后端（偏 AI） | 推理服务化与部署（vLLM / SGLang 生态周边）、LLM 网关与路由、向量检索工程、AI 服务的高并发实践 |
| 通用后端 | 高并发服务、中间件、分布式组件（用通用规则评分，重点看"可写因果链"） |

### 关键词组合示例

- `<项目类型> + <技术栈>`：如 "rag" + "langchain"、"agent" + "workflow"、"llm" + "gateway"；
- 语言过滤：`language:python` / `language:java` / `language:go`；
- 活跃度过滤：`pushed:>2025-10-01`（取近半年，日期按当下时间推算）；
- 排除归档：`archived:false`；
- star 范围见下方「star 立场」。

### 每个候选必须核验的 6 项

1. 许可证（能否自由学习 / 使用）；
2. 近半年是否有提交；
3. issue 是否有响应（排除"弃养"项目）；
4. 文档质量（README / docs / 示例）；
5. 是否有贡献指南、CI、测试；
6. 体量与构建复杂度（用户能否吃透）。

## 三、6 维评分 rubric（1~5 分制）

| 维度 | 权重 | 评分要点（自问） |
| --- | --- | --- |
| 业务真实性 | 15% | 有明确业务场景与用户吗？README 讲的是"解决什么问题"还是技术演示？ |
| 链路可拆分 | 20% | 能否拆出 3 个以上模块/阶段（数据构建→理解→检索→生成→评估）？每个模块有可讲的取舍吗？ |
| 深度挖掘空间 | 20% | 是"调 API 跑通"还是有自己的设计与取舍？有可以"魔改"或自研叙事的点吗？ |
| 指标可写性 | 20% | 项目里有 benchmark / 评估 / 性能讨论吗？能支撑 2~4 个"从 A 到 B"的数字吗？ |
| 岗位族对齐 | 15% | 与用户目标岗位的关键词、技术栈重合度如何？ |
| 区分度 | 10% | 面试官是不是看过很多同款？是否命中红海规则（见 03）？ |

加权求和 → 档位：

- **4.2 以上**：强烈推荐
- **3.6 ~ 4.2**：推荐
- **3.0 ~ 3.6**：备选
- **3.0 以下**：淘汰

### star 立场（不是硬门槛，是信号）

- 优选区间：**200 ~ 10k**；
- 超过 20k：区分度打折——除非用户的目标就是"给知名项目贡献 PR / 拿到贡献者身份"；
- 低于 200：除非逻辑极好（深读后能写出高质量内容），否则信任成本偏高；
- 永远不要只看 star：弃养的高星项目不如活跃的中等星项目。

## 四、红海 / 套路项目排除

执行 `references/03-red-ocean-list.md` 的规则：命中 ≥2 条排除信号 → 直接剔除；命中 1 条 → 标记"红海风险"并降权。

## 五、短名单输出格式

一次给出 3~5 个（不足时见降级策略），按总分排序：

```markdown
### 1. <repo 名称> ⭐<stars>（<语言>）— 评分 4.3/5 【强烈推荐】
- 链接：<URL>
- 一句话定位：<是做什么的、给谁用>
- 匹配点：<对齐画像卡的哪些点>
- 简历增益点：<预计能写出的 2~3 个方向，如"多路召回优化""Agent 工作流设计">
- 红海风险：低 / 中 / 高（原因）
- 上手成本：体量 / 构建难度 / 文档质量
- 建议包装角度：<结合用户背景的一句话>
```

末尾给出**推荐首选**及理由：为什么它比其它候选更适配。并告诉用户两种回复方式：

- "直接采纳首选"（跳过挑选）；
- 指定编号（进入克隆与深读）。

## 六、降级策略

- 严格 rubric 下凑不齐 3 个候选：保底给出 2 个 + 明确说明放宽了哪个维度（如 star 下限、活跃度），不静默降质；
- 一个都找不到：说明卡在哪个维度，给出两条路——放宽哪个条件重搜，或更换项目类型模板再试；
- 用户对全部候选不满意：询问不满意的点（方向 / 难度 / 技术栈），调整画像卡关键词后回炉重搜，最多重搜 2 轮。
